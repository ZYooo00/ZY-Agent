## 0. 專案技術總覽（先講結論）

這是一個**純前端靜態網站 + Firebase Firestore（BaaS）**的架構，**沒有任何後端 Server 或 Google Apps Script（GAS）程式碼**。所有頁面都是 `public/` 目錄下的獨立 HTML 檔（各自內嵌 `&lt;script&gt;` 邏輯），共用兩個 JS 檔：

- `public/shared.js` — 純前端全域常數 + 共用函式庫（**不是 npm 模組，是用 `&lt;script src="shared.js"&gt;&lt;/script&gt;` 直接掛在 `window` 全域**，並非 ES module import）
- `public/firebase-service.js` — Firebase Firestore 存取層（ES module，用 `import` 方式被各頁面用 `&lt;script type="module"&gt;` 引入）

資料庫是 Google Firebase / Firestore（專案 ID `stork11-embryo-lab`），沒有自建 API server、沒有 Cloud Functions、沒有 GAS Code.gs。這點對「新竹院所客製化」規劃非常關键：**目前完全沒有任何後台管理介面**，所有「盤子種類、公式、人員名單、品項清單」都是寫在各 HTML 檔案裡的 JavaScript 常數，要客製化就必須改程式碼、重新部署。

**批號/效期規則**：
- `threshold: { orange_days: 3, red_days: 1 }` 寫死在送出 payload 裡（beipan.html L2912），也是 `shared.js` 的 `calcProductInfo` 的 fallback 預設值（shared.js L394）
- 個別品項的效期警示天數則可透過 `PRODUCTS[].expiryWarnDays`（shared.js）覆寫，但 `threshold` 這組全局值仍是寫死

**與估盤頁面的連動（極重要的隱性耦合風險）**：
- `loadGupanData()`（beipan.html L2985-3064）讀取 `getLatestGupan()` 拿到估盤確認資料，然後用**寫死的 key 陣列**去對應到 beipan 自己的 `givfDishes`/`matrixDishes` **陣列索引**：
  ```js
  const givfKeys = ['opu','de','te','aoa_ci','aoa508','coc','sperm','givf_ph','givf_x'];  // L3031
  const mxKeys = ['d0','bx','tb','geri_szu','geri_fbt','ph','multi'];                      // L3037
  givfKeys.forEach((k, i) =&gt; { if (givf[k] != null) givfDishes[i].plan = givf[k]; });
  ```
  這代表：**gupan.html 的 `givfDishes`/`matrixDishes` 陣列順序，跟 beipan.html 自己另外定義的 `givfDishes`/`matrixDishes` 陣列順序，必須完全一致（用陣列 index 對應，不是用 key 對應）**，而且這兩份清單是分別寫在兩個檔案裡的**兩套獨立資料**。若新竹院所要新增/刪除/調整盤子種類，必須**同時、正確地**修改兩個檔案裡的兩組陣列，稍有順序不一致就會資料錯位而不會報錯（沒有防呆機制）。這是目前最大的技術債，也是後台視覺化設定最需要優先解決的痛點——理想上盤子清單只該存在一個地方（例如 shared.js 的新常數），並用 key 而非 index 做映射。

- 備盤送出後寫入 Firestore `beipan_snapshots`，並把每個試劑批號扣除量、開封瓶數寫進 `kucun_changelog`（`appendKucunLog`），供庫存頁 (`kucun.html`) 用 `calcProductInfo` 計算「目前庫存」——**這是備盤→庫存的連動路徑**。
- 備盤有「多人編輯互斥鎖」機制（`acquireBeipanLock`/`heartbeatBeipanLock`/`releaseBeipanLock`，Firestore collection `beipan_lock`），防止同時間兩人編輯互相覆蓋。

## 4. 頁面之間的連動關係總覽（Firestore Collections 為中心）

```
COLLECTIONS = {
  changelog:       'kucun_changelog',    ← 所有異動的稽核軌跡（append-only）
  jinhuo:          'jinhuo_records',      ← 進貨紀錄
  orders:          'orders',              ← 訂貨單
  pandian:         'pandian_snapshots',   ← 盤點快照
  beipan:          'beipan_snapshots',    ← 備盤快照
  gupan_snapshots: 'gupan_snapshots',     ← 估盤確認快照
  gupan_drafts:    'gupan_drafts',        ← 估盤草稿（跨裝置即時同步）
  beipan_lock:     'beipan_lock',         ← 備盤編輯互斥鎖
}
```
（正式站 prefix 為空、測試站 prefix 為 `test_`，由網域自動判斷，見 firebase-service.js L35-38）

連動路徑：

1. **估盤 → 備盤**：gupan.html 確認後寫入 `gupan_snapshots`；beipan.html 載入時讀 `getLatestGupan()`，透過**寫死的 key 陣列 + 陣列 index**帶入 beipan 自己的盤數輸入框當作預填值（詳見 3.2 節，這是脆弱耦合點）
2. **備盤 → 庫存**：beipan.html 送出時把每個試劑批號的扣除量寫進 `kucun_changelog`（source: `beipan`），kucun.html / order.html 呼叫 `calcProductInfo()` 時會即時用這些 changelog 算出「目前庫存」與批號效期狀態
3. **盤點 → 庫存**：pandian.html 完成盤點時寫入 `pandian_snapshots` + 對應的 `kucun_changelog`（source: `pandian`），若盤點時間晚於最近一次備盤，`calcProductInfo()` 會以盤點快照為庫存計算基準（`stockSource='pandian'`），並在此基準上疊加盤點後的新進貨與手動異動
4. **訂貨 → 進貨**：order.html 建立訂單寫入 `orders`；jinhuo.html 收貨時讀取 `orders`，核銷對應品項的 `receivedQty`/`cancelledQty`
5. **進貨 → 庫存**：jinhuo.html 寫入 `jinhuo_records`；`calcProductInfo()` 讀取所有未作廢進貨紀錄疊加進庫存計算（並非進貨當下直接改一個庫存欄位，而是動態算出來的）
6. **月使用量計算**（給估盤/訂貨參考）：`calcRolling30dUsage()` 讀 `kucun_changelog` 逐日消耗紀錄；沒有消耗紀錄的品項（PVP、Cumulase、Top tips 等非備盤流程品項）則退回用 `calcPandianDeltaUsage()` 讀多期 `pandian_snapshots` 差值估算

整體來說，**除了 gupan↔beipan 那組陣列 index 硬對應之外，其餘連動都是透過 `productId`/`gupanId` 字串 key 對應，資料庫是唯一真實來源（single source of truth 概念上是對的），只是各頁在讀取 Firestore 資料後，還是各自寫了不少 hardcode 的展示邏輯/分組/公式**。

## 5. 後端角色說明

**沒有 Google Apps Script (`Code.gs`)，也沒有任何自建 server（Node/Express/Cloud Functions）**。後端完全由 **Google Firebase** 這個 BaaS（Backend-as-a-Service）扮演：

- **Firestore**：資料儲存（8 個 collections，見上表），走純前端 SDK 直連（`firebase-firestore.js` from CDN），沒有中介 API 層，Security Rules 目前「全開」（firebase-service.js L9 註解明確寫著：`Security Rules 目前全開，上線前必須收緊`），這是安全性待辦但非本次任務重點
- **Firebase Auth**：僅用匿名登入（`signInAnonymously`，firebase-service.js L59），只是為了讓 Firestore 有 auth token 可用，並非真正的使用者身份/權限系統——也就是說系統目前**沒有登入機制、沒有帳號、沒有角色權限**，"人員選單" 純粹是紀錄操作者姓名字串，不是帳號系統
- **無觸發器/Cloud Functions**：像「每月 1 號自動寄送用量報表信件」（CHANGELOG 提到的功能，shared.js L23）等自動化功能，若真的存在，應該是額外部署在別處的 Cloud Function 或排程服務，**在這個 `public/` 目錄看不到任何相關程式碼**，可能需要另外找 Firebase Console 或其他倉庫確認
- `firebase-service.js` 本身採「雙軌寫入」策略（`dualWrite`）：所有寫入先存 localStorage 保底，再嘗試寫 Firestore；讀取則優先 Firestore、失敗才 fallback localStorage —— 這是為了離線可用性設計的降級策略，也代表**目前沒有伺服器端驗證**，資料完整性完全靠前端邏輯把關

## 根因

1. **`beipan.html` 的重置按鈕漏清「草稿」**：橘色測試面板的「重置今日備盤」/「終極清理」呼叫的是 `devResetBeipan()`，這個函式只清了「已送出的備盤快照」，完全沒動到`localStorage` 裡的「草稿」（你打開頁面後每次輸入自動存的那份，key 是 `beipan-draft-2026-07-29`）。「實際備盤」欄位正是被這份沒被清掉的舊草稿蓋回去的——這也是無痕模式（沒有累積的舊草稿）正常、一般視窗（有累積舊草稿）不正常的原因。

2. **我上一輪加的防呆有漏洞**：我加了「草稿如果對應到舊估盤就不套用」的檢查，但只在草稿本身**有**記錄對應估盤版本時才生效。你瀏覽器裡的舊草稿是在我加這個防呆**之前**就存在的，完全沒有這個欄位，等於直接繞過防呆，照樣蓋過去。已經改成：只要現在有載到估盤資料，草稿版本對不上（包含完全沒有版本欄位）就一律當舊資料處理。
